# Десять направлений и режим обновления

Это предлагаемая **редакторская структура вкладок**, а не измеренный рейтинг «самых популярных» областей. Она покрывает интересующие пользователя safety, ускорения, robotics, NLP и visual models, а также смежные исследовательские задачи.

Актуальность широкого охвата сверена с тематикой [ICLR 2026](https://iclr.cc/Conferences/2026/CallForPapers): там перечислены обучение представлений, RL, язык, зрение, оптимизация, теория, безопасность, данные и инфраструктура. Для visual-направления дополнительно использован [CVPR 2026 Call for Papers](https://cvpr.thecvf.com/Conferences/2026/CallForPapers), включающий видео, генерацию, multimodal learning, embodied vision и robotics. Разбиение на десять вкладок и частота проверки ниже — наш проектный выбор.

Периодичность — стартовая рекомендация по организации работы, не оценка фактической скорости публикаций. Для узкой активной подтемы её можно повысить; для зрелой — уменьшить. Пересечения намеренны: например, reward hacking относится и к safety, и к RL. Будущий UI может хранить одну работу и показывать её в нескольких категориях.

Готовые стартовые вопросы, английские поисковые запросы и подпункты есть в `review_forge/topics.json`; `python -m review_forge topics` выводит их без сети. `init --preset <id>` создаёт **один узкий обзор** выбранной категории. Он не создаёт десять обзоров и не запускает генерацию.

## Делать один раз или обновлять

Для вашего замысла подходит **живой обзор со стабильным ядром и версионируемыми дополнениями**.

Объяснения базовых понятий, исторический маршрут и вводные материалы могут долго оставаться неизменными. Список свежих работ, экспериментальные сравнения, ограничения и нерешённые вопросы требуют проверки по мере появления существенных свидетельств. Еженедельная генерация всего текста без новых оснований создаёт редакторский шум и расходует API.

Практический цикл:

1. Сначала один базовый обзор на ограниченную подтему и дату.
2. Раз в неделю или две — только поиск: `check-updates`. Сохраняются новые кандидаты, изменённые метаданные, ошибки провайдеров и всё ещё не просмотренные записи.
3. Если есть релевантное новое свидетельство — отбор и обработка. Обновление версии arXiv также может потребовать перечитывания источника.
4. Пересобрать синтез и сохранить новый снимок; старый остаётся доступен. Проверить, почему изменились выводы, а не только количество статей.
5. Если новых существенных данных нет — сохранить прежний обзор. Нулевой результат ограниченного поиска не равен доказанному отсутствию новых работ.

Текущая реализация пересобирает общий синтез, когда его входные тезисы меняются; неизменившиеся запросы модели берутся из кеша. Обновление отдельного абзаца с сохранением всей авторской редакции — возможное следующее расширение. Не заявляется, что такая редакционная система уже реализована.

## Интерфейс библиотеки

Достаточно десяти категорий, внутри — несколько узких обзоров. Для каждого обзора полезны вкладки «Обзор», «Понятия», «Статьи», «Доказательства», «Новые работы», «История».

Статический UI уже реализован: `python3 -m review_forge serve --open`. В нём десять направлений и разделы «Обзор», «Источники», «История». Читатели не могут запускать поиск и генерацию. Он показывает только выпущенные через `release` версии, а приватный цикл `maintain`/`watch` готовит новые черновики отдельно. Сейчас поддерживается один обзор на категорию; несколько узких обзоров внутри неё потребуют изменения каталога. Готовых научных материалов пока нет.

Отдельно стоит хранить дату последнего поиска и дату последней содержательной версии. «Проверено сегодня» и «текст изменён сегодня» — разные сведения. Модельную критику также нельзя показывать как знак ручной научной проверки.
