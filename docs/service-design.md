# Идея сервиса, ограничения и варианты развития

Обновлено 28 октября 2026. Ниже разделены работающий код, проектные рекомендации и ещё не проверенные гипотезы о пользе. Реальные обзоры в этой работе не генерировались.

## Какую задачу решать

Ценность сервиса — помочь человеку быстро ответить: **что это за проблема, какие объяснения/методы существуют, почему им можно доверять, где они расходятся и что стоит прочитать дальше**. Ещё один поток аннотаций сам по себе эту задачу не решает.

Исходный grokking-проект ценен картотекой «понятие → позиции работ → конкретные утверждения → места в первоисточниках». Наш автоматический процесс должен готовить и поддерживать такую структуру. Красивый связный текст — один из способов её показать. Подробный разбор примера и критерии находятся в `review-standard.md`.

Рабочая единица — ограниченный исследовательский вопрос. «Robotics» слишком широко для одного обстоятельного обзора. «При каких условиях VLA переносится между роботами?» уже задаёт предмет отбора и сравнения. Десять вкладок — навигация по областям, а не обещание исчерпывающего обзора каждой области. Сейчас в каждой предусмотрена одна узкая стартовая тема.

Полезный маршрут читателя:

1. За пять минут понять вопрос, основные понятия, выводы и их границы.
2. При желании углубиться в сравнение подходов и реальные разногласия.
3. Перейти от любого важного вывода к источнику и условиям эксперимента.
4. При следующем визите увидеть, что изменилось в понимании и почему.

## Как должен работать цикл

```text
КОМПЬЮТЕР ВЛАДЕЛЬЦА
Вопросы/критерии → поиск → кандидаты → отбор → чтение источников
  → тезисы с доказательствами → понятия/сопоставление → критика → черновик
  → проверка содержания редактором → решение о выпуске → сборка site/

СТАТИЧЕСКИЙ ХОСТИНГ
Готовые HTML/CSS/JS/JSON → читатель: обзор / источники / история
```

Публичный сайт не принимает исследовательские задания и не содержит модельных ключей. Количество читателей не запускает новые платные генерации. У статического хостинга всё равно остаются обычные расходы/ограничения трафика и домена; нулевую стоимость никто не гарантирует.

Частота поиска и частота выпуска — разные вещи. Можно раз в неделю проверять литературу и месяцами не менять хороший вводный раздел. Поводом к выпуску могут быть изменившийся вывод, обнаруженная ошибка, новый способ решения, существенное ограничение прежнего метода или важная репликация. Дополнительные подтверждения тоже бывают полезны, даже когда общий вывод остаётся прежним. Одна новая статья не является автоматическим поводом переписывать весь обзор.

Это согласуется с принципом проверки необходимости обновления в [руководстве Cochrane](https://www.cochrane.org/authors/handbooks-and-manuals/handbook/current/chapter-iv): учитываются важность вопроса и влияние новой информации. Прозрачные вопросы, стратегия поиска и причины отбора близки принципам отчётности [PRISMA](https://www.prisma-statement.org/prisma-2020-checklist). Здесь заимствованы отдельные принципы evidence synthesis; проект не заявляется PRISMA-compliant systematic review и не переносит медицинскую методологию целиком на AI research.

## Что уже реализовано

| Часть | Реальное состояние кода | Граница возможности |
|---|---|---|
| Постановка вопроса | TOML, критерии включения/исключения, даты, десять узких пресетов | Качество формулировки требует редактора |
| Обнаружение работ | arXiv, Semantic Scholar, ограниченная выдача, накопление кандидатов, сырые ответы, ручной импорт | Нет полного охвата, прямых ACL/CVF/OpenReview-коннекторов или citation snowballing |
| Отбор | Модель по метаданным/аннотациям, причины решений, приоритет человеческих решений, deferred по бюджету | Модель может ошибочно исключить важную работу; cap ограничивает охват |
| Чтение | PDF/TXT/Markdown, сохранённые версии и хеши, сегменты с локаторами | Нет OCR и понимания изображений; качество таблиц/формул не гарантируется |
| Тезисы | Тип утверждения, условия, ограничения, цитата, ссылка на сегмент | Совпадение текста не доказывает логическое следование вывода |
| Синтез | Связный обзор, карточки понятий, различия позиций, ссылки на тезисы, модельная критика | Синтез получает ограниченную выборку тезисов; критик может разделять ошибки автора |
| Проверки | ID/схемы/цитаты/ссылки, актуальность входов, обязательный полный текст по умолчанию | Это механические проверки, не экспертиза результатов исследований |
| Обновления | `maintain`/`watch`, повторный поиск, сравнение выбранного корпуса, кеш и новые приватные снимки | Нет семантического решения «вывод X надо изменить» и точечной правки разделов |
| Выпуск | Отдельный manifest выбранных редактором снимков, проверка checksum, публичная сборка | Редакторский флаг сам по себе не доказывает качество проверки; upload не реализован |
| Сайт | Десять направлений, обзор, источники, история, HTML/BibTeX; только чтение | Сейчас один обзор на категорию; нет готовых научных обзоров |

Код интеграций написан, но живые API, фактические расходы и научное качество не проверялись. Локальные тесты подтверждают технические свойства отдельно от качества будущего исследования.

## Где могут возникнуть проблемы

**1. Узкая выдача выглядит как полная карта области.** Поисковые формулировки, лимит результатов и выбор базы определяют, что система вообще увидит. Важные старые работы и отрицательные результаты могут не попасть в корпус. Нужны проверенные исходные статьи, ручная библиография, позже — обход цитирований. Нельзя подписывать нулевой результат как «ничего нового в области».

**2. Уверенный текст скрывает слабое основание.** Цитата может быть настоящей, но относиться к другому утверждению или поддерживать более узкий вывод. Нужно проверять основные выводы и противоречия по полному источнику, отдельно отмечать авторский результат и редакторскую интерпретацию. Ещё одна модель полезна как проверка, но не независимая научная гарантия.

**3. Сравниваются несопоставимые условия.** Для ускорений имеют значение GPU, модель, batch, длины последовательностей, latency/throughput и стоимость; для safety — модель угроз и адаптивность атак; для robotics — среда, робот, задачи и данные обучения. Одна таблица «кто лучше» без этих условий будет вводить в заблуждение. Структурированные условия уже есть у тезисов; полноценные сравнительные матрицы по специфике области ещё предстоит сделать.

**4. Рост корпуса ломает экономику и охват.** По мере накопления кандидатов отбор достигает max_candidates, а релевантные статьи откладываются по max_papers. Сейчас превышение лимита не маскируется успехом. Потребуются разделение обзора на подтемы, обслуживание решений и оценка стоимости на первом реальном запуске. Общий бюджет модели ограничивает обращения, а не гарантирует сумму в валюте. Для прохода десяти тем лимит применяется отдельно к каждой теме.

**5. «Автоматически» требует обслуживания.** Спящий Mac, остановленный процесс, rate limits, недоступный PDF и изменившийся API прерывают цикл. `watch` не является установленной службой. Нужно читать ошибки мониторинга, обслуживать диапазон дат (пресеты до 2026), а позднее добавить системное расписание и уведомление только об ошибке/значимом черновике. Метаданные не всегда сообщают о смене байтов удалённого файла; для этого есть явное перечитывание источников.

**6. Еженедельная генерация разрушает стабильность.** Модель может переименовать понятия, иначе сгруппировать статьи или переписать верный абзац без новых оснований. Текущий фильтр неизменного корпуса уменьшает это, но не решает выравнивание понятий между версиями. Нужны устойчивый словарь, сохранение редакторских правок и изменения по конкретным утверждениям. Сейчас пересобирается общий синтез.

**7. Автоматизация масштабирует ошибки и редакторскую очередь.** Десять еженедельных больших черновиков могут создать больше работы, чем удастся прочитать. Начинать полезнее с одной знакомой узкой темы, оценить качество и время проверки, затем расширяться. Не требуется заранее заполнять все вкладки или выпускать материал по календарю.

**8. Доступный PDF не означает право на перепубликацию.** Публичный пакет исключает оригиналы и приватные журналы, но содержит короткие цитаты. Права и объём опубликованных фрагментов проверяет владелец. Автоматического юридического заключения нет.

## Как может выглядеть продукт

| Вариант | Для кого и какая польза | Издержки |
|---|---|---|
| Концептуальный атлас | Изучить тему с нуля: определения, карта методов, маршрут чтения | Хорошая первая версия требует глубокой редакторской работы; обновлять можно редко |
| Радар/дайджест | Следить за областью: несколько отобранных новинок и почему они интересны | Быстрее готовить выпуск, но без базового контекста новичку трудно ориентироваться |
| Живой учебник + журнал изменений | Понять основу и следить только за существенными дополнениями | Нужно связывать новые свидетельства с устойчивыми понятиями и выводами |
| Справочник для выбора метода | Решить практическую задачу: условия, варианты, компромиссы, требования | Сравнимость цифр и экспериментальных условий требует особенно строгой проверки |

Предлагаемый основной вариант — **живой учебник со стабильным ядром и коротким журналом значимых изменений**. Радар может быть приватной входящей очередью, из которой лишь часть работ влияет на публичный текст. Если у владельца мало времени на редактуру, лучше небольшой качественный атлас с редкими выпусками.

## Что добавить и что отложить

**Ближайший приоритет:** проверить один реальный узкий обзор, когда будет разрешён запуск. До масштабирования оценить: помогает ли он ответить на вопросы; сколько времени экономит; корректны ли основные выводы; сколько важных работ пропущено; сколько времени и денег занимает проверка. Число статей и длина текста — технические счётчики, не метрики полезности.

**Дальше по содержанию:** короткое резюме и prerequisites; маршрут «сначала это → потом это»; сравнительная таблица с условиями; явно выделенные согласие/споры/неизвестное; ссылки от важных выводов к первоисточникам. Для каждого выпуска — «было → стало → основание → почему это важно». Не заменять уверенность в выводе произвольным процентом, выданным моделью.

**Дальше по процессу:** семантическая карточка влияния новой работы на существующие выводы; сохранение редакторских правок; стабильные ID понятий; несколько узких обзоров в категории; обслуживание библиографии/версий/retractions; надёжное локальное расписание и сигнал о проблеме. Эти функции пока не выдаются за готовые.

**Отложить:** публичный чат с моделью, генерацию посетителями, аккаунты, обязательную еженедельную перегенерацию, полные переводы всего корпуса, огромный интерактивный граф на первой странице и рейтинг всех методов по одному числу. Они увеличивают сопровождение до того, как доказана польза основного материала.

Для первого публичного выпуска можно скрыть пустые категории или оставить их честно помеченными. Сейчас выбран второй вариант, чтобы видеть структуру будущей библиотеки. Ни статьи, ни научные выводы для заполнения интерфейса не придуманы.
