Короткий ответ

Общая память может означать обмен промежуточными результатами внутри одной задачи, перенос опыта между задачами или обмен знаниями между пользователями. Эти механизмы требуют разных проверок. Отбор полезного опыта и контроль того, кому он доступен, — разные задачи. Retrieval сам по себе не решает права доступа, устаревание и перенос чужих предпочтений. Границы: память или обучение?

Редакторское предложение. Мы рассматриваем collaborative learning через внешнюю память LLM-агентов: write, retrieval, consolidation и revision. Federated learning, обмен градиентами и совместное обновление весов остаются вне этого разбора.

Редакторское предложение. Поиск 22 ноября 2026 года: первичные работы о shared/collaborative/cross-agent memory; выбраны семь механизмов и типов проверки. Это начальная подборка; новые ноябрьские кандидаты и более широкий корпус требуют отдельного разбора.

Где общий опыт становится проблемой

Много записей не обязательно лучше: шумный admission увеличивает контекст, а исходный опыт может быть неправильным или содержать неприменимые предпочтения. Сравнивать следует при одном retrieval budget. Learning to Share: Selective Memory for Efficient Parallel Agentic Systems Learning from Others, Acting for You: Cross-User Memory Sharing for LLM Agents

Дедупликация и обновление фактов могут конфликтовать: похожая новая запись бывает именно исправлением. В production-исследовании synchronous near-duplicate gate мог не пропустить запись до проверки противоречия. Governed Shared Memory for Multi-Agent LLM Systems

Согласие нескольких агентов не является независимым подтверждением, если все прочитали одну ошибочную память. Для визуальных задач важно хранить исходное свидетельство и контекст наблюдения. Collaborative Memory for Multi-Agent VLM Systems

Признаки переноса на reasoning benchmarks не доказывают безопасное применение между пользователями. Успех задачи, отсутствие утечек и верное разрешение конфликта надо проверять отдельно. Минимальная честная проверка

Редакторское предложение. Сравнить без памяти, локальную память, общий пул без фильтра и общий пул с отбором. Зафиксировать модели, инструменты, число агентов и бюджет retrieval/calls; учесть стоимость записи и консолидации.

Редакторское предложение. Разделить донорские и тестовые задачи до построения памяти, проверить пересечение по содержанию. Создать тесты на смену предпочтений, противоречащую запись, отзыв доступа и повторную выдачу старого факта.

Редакторское предложение. Сохранять success, latency, tokens и memory size отдельно от leakage, stale-read и отрицательного переноса. Мы не запускали этот эксперимент; это предлагаемый протокол.

Следующая проверяемая гипотеза

Редакторское предложение. Гипотеза: переносить проверенные обобщённые процедуры с явным scope полезнее, чем целые ответы. Условия: одинаковые донорские траектории, замороженный тест, одинаковый retrieval budget; контроль — локальная память и сырой общий пул.

Редакторское предложение. Опровержение: выигрыш пропадает после удаления похожих тестовых задач или учёта расходов consolidation; либо появляются утечки и отрицательный перенос сверх заранее установленного порога. Отдельная проверка — исправление ошибочного донора и зависимых записей.
